Privacy Notice

Last updated: 14 October 2026. This is a practical draft based on the code currently available; it is not a guarantee of legal compliance.

About this notice

This notice covers the public ProtoxTap website, the hosted NFC-card redirection service and the separate administration tools visible in the project. ProtoxTap is the service name. The legal identity and contact address of the operator have not been confirmed in the available project information; those details and the operator's data-controller role must be confirmed before launch where required.

For a privacy question, contact protoxbusinesses@gmail.com or call 07923 910153.

Information the service handles

Business and account information

The administration system can store a business name, contact name, email address, phone number, notes and a Google Place ID. These details are entered by an administrator when creating or updating a business record. The project does not contain a public customer account or sign-up form.

Cards and service events

The database stores card identifiers, the associated business, configured redirect destination, card status and creation, activation and deactivation times. It stores event type and timestamp records for service events, including active card taps. A tap event is associated with a card record; the current event schema does not store a visitor's name, IP address or user-agent string. The public card route records an event for an active card before redirecting it. An inactive card is directed to the inactive-card page instead.

Card event history may remain in the database until an administrator removes it with the card record. The code has no general event-retention schedule. A forced card deletion removes its event records; ordinary deletion is blocked while history exists.

Administration and authentication

Administrative records include a username and a password hash. The code hashes passwords using scrypt with a random salt. Successful sign-in creates a random session token; a hash of the token is stored in the database. The browser receives a protoxtap_session cookie configured as HttpOnly and SameSite=Lax, with a seven-day expiry. The current code does not set the Secure cookie attribute; deployment configuration must be checked and this should be addressed before production use. Expired session records are removed when checked by the application.

Administrative action records are created for card operations and can include the administrator, action, card or related business identifiers and labels, event time and action-specific details. They are not a complete record of every administration action and do not have a configured retention period in the code.

Some backend diagnostic logging writes business names, Google Place IDs, administrative session-record values and error details to the application console. The production log destination, access controls and retention period are not identified in this project. These logs need an owner review and appropriate minimisation before launch.

Why information is used

  • Business and card records are used to configure and operate hosted card redirection.
  • Tap and card-lifecycle events are recorded to operate the service and maintain service history. A customer-facing analytics dashboard is not currently available.
  • Account information and session records support restricted administration.
  • Administrative action records provide a history of changes made through the administration tools.

The operator has not documented a lawful basis for each purpose. The appropriate lawful basis, any additional purposes and the operator's controller/processor roles must be determined before launch; no specific lawful basis is asserted by this draft.

Cookies, storage and analytics

The public landing and legal pages do not set cookies or use local storage, session storage, analytics scripts or advertising trackers in the code inspected. They do not load third-party fonts, scripts, images, embeds or stylesheets. The Protox Webpages link and email links only contact those destinations if you choose to follow them.

The separate administration sign-in uses the session cookie described above. No browser local-storage or session-storage use was found in the administration source inspected. Hosting, proxy and infrastructure logs may process technical request data; the providers and their log settings have not been identified in this project, so this notice cannot confirm whether those providers record IP addresses or how long they retain logs.

Recipients and external services

Business, card, session and administrative records are stored through a PostgreSQL database connection. The hosting and database providers, locations, contractual terms and any other infrastructure recipients are not identified in the source code available for this review and must be documented by the operator.

The administration backend sends a business name to the Google Places API when an administrator creates or updates a business record to look up a Place ID. When a customer taps an active card, the browser is redirected to the configured review destination, which in the current card-assignment code is a Google review link. Google then handles the request under its own terms and privacy information. The public landing page itself does not embed a Google interface.

The website links to Protox Webpages and opens an email draft through the visitor's configured email handler only when those links are used. Those destinations have their own privacy practices.

Security and retention

The code uses password hashing with scrypt, random session tokens and stores a hash of each session token. These implementation details are not a guarantee of security. The production transport-security configuration, database access controls, backups, hosting safeguards, incident process and retention periods have not been verified. The operator must confirm those arrangements and set appropriate retention periods before launch.
